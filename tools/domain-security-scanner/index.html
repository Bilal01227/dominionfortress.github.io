Understand the findings before changing anything

The scanner checks publicly observable configuration signals. A missing header or DNS record is a prompt for review, not automatic proof of an exploitable vulnerability. The right configuration depends on the application, hosting environment, email architecture and business requirements.

What the checks cover

HTTPS and transport security: confirms whether the public endpoint responds over HTTPS and whether HTTP Strict Transport Security is visible. HSTS should be enabled only after HTTPS is correctly deployed across the intended hostnames.

Security headers: checks common browser controls such as Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy and Permissions-Policy. Header absence may be intentional for some applications; policies must be tested to avoid breaking legitimate functionality.

DNS and email: reviews public A, AAAA, MX, NS, SPF and DMARC signals. These checks do not inspect private cloud settings, mailbox security or every subdomain.

Public security files: looks for resources such as robots.txt, sitemap.xml and security.txt. Their presence is not a security certification.

What is outside the scan

This passive check does not exploit vulnerabilities, authenticate to systems, enumerate private assets, test application logic or verify compliance. It is not a penetration test and should not be used to assess a domain without permission.

Suggested remediation workflow

  1. Confirm the domain and every hostname in scope are owned or authorised.
  2. Review each finding against the actual application and hosting architecture.
  3. Prioritise exposed sensitive services, weak transport configuration and controls relevant to real data flows.
  4. Apply changes in a test environment where possible, then validate application behaviour.
  5. Retest externally and document the change, owner and residual risk.
